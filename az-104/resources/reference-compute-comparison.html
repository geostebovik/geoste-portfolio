Azure Compute — When to choose each

VM vs App Service vs
Container Instances vs Container Apps

Every Azure compute decision starts with the same question: how much of the stack do you want to manage? The four options represent a spectrum from full control to full abstraction. Think of it as owning a house, renting an apartment, booking a hotel room, or joining a co-living space with on-demand staff — most control in the house, least hassle in the co-living space, but you can't repaint the hotel walls.

ACI concept
Container Group
Two or more containers sharing the same host, IP address, and localhost. Analogous to a Kubernetes Pod. Use when a sidecar (e.g. a log shipper) must run alongside the main container on the same machine. Scheduled and billed as a single unit.
ACA concept
Container App Environment
The shared infrastructure boundary for one or more Container Apps — the apartment building to each app's tenant unit. Owns the VNet subnet (delegated, min /23), shared ingress controller, Log Analytics workspace, and internal DNS. One CAE is required per group of Container Apps.

⚠ The exam trap — three container scenarios
The word "container" appears in all three container services. The exam exploits this. The decision driver is always the workload pattern, not the packaging format. Ask: does it run continuously? Does it need to scale? Is it a one-shot job?
Containerized web app serving users continuously — needs slots and TLS
→ App Service (container mode)
Containerized job that processes a queue and exits — no scaling needed
→ Container Instances
Containerized microservice or API — needs auto-scale and traffic splitting
→ Container Apps
Container service distinctions

App Service + containers — App Service can run container images instead of code. The platform remains App Service: slots, autoscale, auth, and TLS all still work. The container is just the delivery mechanism, not a different service. Use this when your team already has a container build pipeline and wants App Service's operational features without rewriting deployment tooling.

Container Instances + Container Groups — A container group is an ACI-only concept: two or more containers sharing the same host, IP, and localhost. Think of it as a Kubernetes Pod equivalent in Azure. Use it when a sidecar container must run alongside the main container — for example, a log-forwarding agent that reads from the same filesystem. ACI has no built-in scaling; it is the right choice when you want to start a container, run a task, and stop paying.

Container Apps + Container App Environment — Every Container App must live inside a Container App Environment (CAE). The CAE owns the VNet subnet (delegated to Microsoft.App/environments, minimum /23), shared ingress, Log Analytics, and internal DNS. Think of the CAE as the apartment building and each Container App as a tenant unit. ACA adds revision management (blue/green deployments), percentage-based traffic splitting between revisions, and KEDA-based event-driven autoscaling — capabilities that ACI simply does not have.
